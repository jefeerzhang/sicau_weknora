## Problem Statement

当前 WeKnora 把平台级 `is_system_admin`、空间内 `owner/admin/contributor/viewer` 和公开注册/自助建空间组合在一起，导致权限边界与教学场景不一致：普通注册用户可能创建个人工作空间并成为 Owner，系统管理员也可以有多个，且现有 bootstrap 只能提升已经注册的用户，不能建立部署时唯一的初始管理入口。工作空间成员页还直接展示“所有者 / 管理员 / 编辑 / 访客”并允许通过下拉框提升成员，这既让教育用户误以为平台身份可以在空间内授予，也允许教师把其他账号变成自己空间的管理者。教师之间需要明确的空间隔离，学生不能获得开设空间或管理成员的能力。

教学部署需要一个可审计、默认拒绝的组织架构：部署时只有一个初始化超级管理员；超级管理员自动具备教师能力并可指定多个其他教师；超级管理员和其他教师分别创建和管理自己的工作空间；学生只能被教师邀请进入并使用被授权空间。模型服务由各教师按空间配置，超级管理员不承担统一模型供给和凭据托管。

## Solution

建立平台级唯一超级管理员（SuperAdmin）作为权限分发起点。其账号和初始密码在部署初始化阶段设定，并通过强制改密或一次性初始化流程完成首次登录。SuperAdmin 自动包含教师端能力，可以创建和管理自己开设的工作空间；只有 SuperAdmin 可以任命或撤销其他教师身份。任何公开注册、学生操作或教师操作都不能把账号提升为教师或 SuperAdmin。

教师身份允许多个。SuperAdmin 与被任命教师都可以创建多个属于自己的工作空间，并作为“空间负责人”维护知识库、Agent、学生成员和模型配置；除平台级审计/故障恢复动作外，任何教师都不能查看、修改或管理其他教师的工作空间。学生账号不具备创建工作空间能力，只能通过教师邀请进入一个或多个工作空间，以“学生”关系使用知识资源。

平台身份与空间关系必须分层呈现。用户信息页只读展示“超级管理员（教师）/ 教师 / 学生”；SuperAdmin 在教师管理页任命或撤销教师；工作空间成员页只展示“空间负责人 / 学生”，不提供角色下拉框。实现层可以继续用 `owner` 和 `viewer` 执行授权，但教育界面不暴露通用的“所有者 / 管理员 / 编辑 / 访客”角色，也不得通过成员接口创建 `admin` 或 `contributor`。

公开的 Owner 自助注册和个人空间自动创建必须关闭。普通账号创建采用教师邀请流程（或由受授权的管理流程创建学生账号）；邀请只能授予学生使用权限，不能通过邀请生成教师、管理员或 Owner。所有平台级和空间级授权检查均默认拒绝，RBAC 强制模式必须开启。

模型配置按工作空间隔离。每名教师为自己的工作空间配置对话、向量化、重排、视觉/语音等需要的模型及凭据，承担对应的费用和配额。学生可以调用已配置模型，但不能读取、导出或修改凭据；SuperAdmin 只能审计配置状态，不能看到明文凭据。没有完成配置时，问答返回明确的配置缺失错误，不自动回落到平台模型。

## User Stories

1. As a deployment operator, I want to initialize exactly one SuperAdmin account with a predefined credential, so that there is a deterministic authority for the first login.
2. As a deployment operator, I want the initial credential to be changeable after first login, so that the bootstrap secret is not permanent.
3. As a SuperAdmin, I want to see all users, teachers, and workspaces at platform scope, so that I can audit the organization.
4. As a SuperAdmin, I want to appoint an existing account as a teacher, so that teacher identities come from an explicit approval action rather than self-registration.
5. As a SuperAdmin, I want to appoint multiple teachers, so that the platform supports multiple courses or teaching teams.
6. As a SuperAdmin, I want to revoke a teacher appointment, so that a departed teacher can no longer create or manage teaching workspaces.
7. As a SuperAdmin, I want teacher appointment and revocation actions to be audited, so that privilege changes are reviewable.
8. As a SuperAdmin, I want to remain the only platform authority, so that no teacher or student can appoint another SuperAdmin.
9. As a SuperAdmin, I want protection against removing the last SuperAdmin, so that the deployment cannot become ownerless.
10. As a SuperAdmin, I want to reset a teacher or student password without exposing the new password in logs, so that account recovery is operable and confidential.
11. As an appointed teacher, I want to log in only after being appointed by the SuperAdmin, so that teacher access is centrally controlled.
12. As a SuperAdmin, I want teacher capabilities automatically available to my account, so that I can operate a teaching workspace without appointing myself.
13. As a SuperAdmin, I want to create and own my own workspaces while retaining platform authority, so that I can teach directly when needed.
14. As a teacher, I want to create a workspace after appointment, so that I can establish a course-specific knowledge area.
15. As a teacher, I want to create more than one workspace, so that I can separate courses, cohorts, or projects.
16. As a teacher, I want to become the owner of workspaces I create, so that I can maintain their content and members.
17. As a teacher, I want to invite students to my workspace, so that students can use the course knowledge area.
18. As a teacher, I want all invitation and member-add flows to grant only the Student relationship, so that no workspace workflow can mint a Teacher, SuperAdmin, or elevated workspace role.
19. As a teacher, I want to remove students from my own workspace, so that course access can be revoked without changing anyone's platform identity.
20. As a teacher, I want the member list to identify me as the workspace lead without exposing generic RBAC terminology, so that the screen matches the teaching organization.
21. As a teacher, I want to configure the models and provider credentials for my own workspace, so that I control quality, cost, and quota for that course.
22. As a teacher, I want model credentials encrypted at rest and redacted from responses, so that provider secrets remain private.
23. As a teacher, I want to see whether my workspace models are configured and healthy, so that I can fix setup before students ask questions.
24. As a teacher, I want a clear error when a required model is missing, so that failures are actionable instead of silently using an unexpected provider.
25. As a SuperAdmin, I want to manage my own teaching workspaces without receiving implicit daily control over another teacher's workspace, so that platform governance and teaching ownership remain distinct.
26. As a teacher, I want to manage my own workspace without seeing another teacher's workspace members, content, settings, or credentials, so that teaching spaces remain isolated.
27. As a teacher, I want to use more than one workspace I own, so that my account can support multiple teaching contexts.
28. As a student, I want to register only through a teacher invitation, so that arbitrary visitors cannot create teaching accounts or personal workspaces.
29. As a student, I want an accepted invitation to place me directly in the invited workspace, so that onboarding has no unrelated workspace-creation step.
30. As a student, I want to use documents, Agents, and configured models in an authorized workspace, so that I can complete course learning tasks.
31. As a student, I want my default role to be `viewer`, so that I cannot change course resources or member permissions.
32. As a student, I want to access multiple workspaces when multiple teachers invite me, so that one account can serve several courses.
33. As a student, I want to see only my own pending invitations and authorized workspaces, so that other students' identities and private spaces are not exposed.
34. As a student, I want model credentials hidden from the UI, API responses, logs, and exports, so that I cannot reuse a teacher's provider account.
35. As a student, I want a useful setup error when a teacher has not configured a required model, so that I know the issue is workspace setup rather than my account.
36. As an unauthenticated visitor, I want public registration and self-service workspace creation disabled, so that the deployment is not an open owner factory.
37. As any authenticated user, I want attempts to create a workspace without teacher authorization to return a clear 403, so that the permission boundary is consistent across UI and API.
38. As any authenticated user, I want attempts to appoint a teacher or SuperAdmin without platform authority to return a clear 403, so that privilege escalation cannot occur through direct API calls.
39. As a security auditor, I want cross-workspace access checks to enforce tenant isolation even when a user knows another workspace ID, so that identifiers cannot bypass authorization.
40. As a security auditor, I want denied role checks recorded with actor, workspace, action, and outcome, so that repeated probing is detectable.
41. As an operator, I want the system to fail closed if RBAC configuration is missing or disabled in production, so that a configuration mistake cannot turn every member into an effective Admin.
42. As an operator, I want migration behavior for existing Owners, Admins, and SystemAdmins documented, so that upgrading an existing deployment does not silently broaden access.
43. As a teacher, I want student conversations to remain private to the student unless a separately approved teaching feature says otherwise, so that workspace membership does not imply access to personal conversation content.
44. As any authenticated user, I want my platform identity shown read-only in my profile, so that I can distinguish platform authority from my relationship to the current workspace.
45. As a SuperAdmin, I want Teacher appointment to remain exclusively in the platform Teacher-management page, so that a workspace lead cannot create Teachers through a member-role dropdown.
46. As a workspace lead, I want the workspace member page to show only “空间负责人” and “学生”, so that users do not confuse workspace authorization with platform identity.
47. As a student, I want the workspace member page to have no role-promotion control, so that direct UI interaction cannot grant me management capabilities.
48. As a security auditor, I want direct member-role API requests for `owner`, `admin`, or `contributor` rejected, so that hiding the dropdown is not the security boundary.
49. As an operator upgrading an existing deployment, I want legacy `admin` and `contributor` memberships downgraded to `viewer` with an audit record, so that historical generic roles do not preserve unintended teaching privileges.
50. As an operator upgrading a workspace with multiple legacy Owners, I want the migration to require an explicit responsible Teacher instead of choosing silently, so that ownership is not transferred by guesswork.

## Implementation Decisions

- Introduce explicit platform roles and invariants: exactly one active SuperAdmin at bootstrap, zero or more appointed Teachers, and Students as the default non-teaching identity. SuperAdmin is a composite identity that automatically satisfies the Teacher capability floor. Preserve the distinction between platform authority and workspace membership roles.
- Replace the current multi-SystemAdmin interpretation with a single SuperAdmin authority for appointment operations. If backward compatibility requires retaining the existing flag, enforce a database/application invariant that only one active account can carry the highest platform role and provide an explicit migration for existing administrators.
- Bootstrap must create or atomically initialize the first SuperAdmin account and credential. It must not promote an arbitrary first registrant. The bootstrap credential is one-time/rotatable, and startup must refuse ambiguous initialization states rather than silently selecting a user.
- SuperAdmin-only endpoints manage teacher appointments, revocations, platform user status, and platform audit views. Teacher endpoints cannot mutate platform roles.
- Teacher appointment is a prerequisite for ordinary teacher workspace creation; SuperAdmin is exempt because Teacher capability is inherited. Workspace creation requests must evaluate the caller's effective platform identity, not only a tenant role or client-controlled request field.
- A workspace has one responsible Teacher. The creator receives the internal `owner` role and the education UI displays it as “空间负责人”. A Teacher can manage only workspaces where that Teacher is the responsible owner. SuperAdmin can manage workspaces it creates through the same teacher path; its separate platform authority is reserved for platform audit and narrowly scoped recovery, not implicit day-to-day control of other teachers' workspaces.
- Existing tenant RBAC remains the internal enforcement mechanism, but the teaching deployment admits only two active membership states: `owner` for the single workspace lead and `viewer` for students. The generic `admin` and `contributor` states are not assignable through teaching routes or UI. Production deployments must keep enforcement enabled; fail-open observation mode is not an acceptable production default.
- Public self-service registration is disabled. The default provisioning mode for non-bootstrap users is tenantless until a valid teacher invitation is accepted; no registration path may create a personal workspace or Owner membership for an unappointed account.
- Student onboarding uses teacher invitations. Invitation links, email invitations, and direct member-add flows are fixed to `viewer`. Member-role mutation requests that attempt `owner`, `admin`, or `contributor` are rejected even when made by the workspace lead. Teacher appointment remains a separate SuperAdmin-only platform mutation.
- A student may belong to multiple teacher workspaces, with independent membership rows and no cross-workspace role inheritance.
- Teacher workspace model configuration is tenant-scoped and independent per workspace. Supported model categories follow the existing model service contracts; credentials are encrypted at rest, redacted from DTOs/logs/audit details, and never returned to viewers.
- Model invocation resolves the selected workspace configuration. Missing or invalid required configuration returns a typed, actionable setup error; there is no implicit SuperAdmin-provided fallback.
- SuperAdmin audit access exposes configuration status and security events without exposing plaintext provider credentials or student conversation bodies.
- All privileged mutations must be available through guarded backend routes first; frontend controls mirror the same capability checks and are not relied upon for security.
- Existing workspaces and memberships require an explicit migration policy: identify current SystemAdmins, map approved accounts to SuperAdmin/Teacher/Student, disable personal workspace creation, retain the single responsible `owner`, and downgrade legacy `admin`/`contributor` memberships to `viewer` with an audit record. A workspace with zero or multiple legacy Owners is ambiguous and must require an explicit SuperAdmin resolution; migration must not silently select a responsible Teacher.
- The workspace member page removes the role selector. It derives presentation labels from the allowed workspace relationship: internal `owner` is “空间负责人” and internal `viewer` is “学生”. It does not expose another member's platform identity. The profile page and SuperAdmin Teacher-management page remain the authoritative platform-identity surfaces.
- Legacy or unexpected membership values are not relabeled as Student or Teacher. Until migrated, they are shown as an exceptional legacy role without mutation controls, so the UI cannot conceal unresolved elevated access.
- API keys and cross-tenant operator bypasses must not implicitly grant teacher appointment or SuperAdmin capabilities unless a separately declared platform capability is present.

## Testing Decisions

- Tests assert externally visible authorization behavior, response status/error shape, persisted role/membership effects, isolation, and secret redaction. They must not assert private helper structure or implementation-specific call ordering unless that ordering is the security contract.
- Highest seam: authenticated HTTP handler/router tests with controlled service doubles. This exercises route guards, identity extraction, request validation, and response behavior in one place while avoiding full deployment setup.
- Bootstrap seam: startup/bootstrap tests cover first initialization, duplicate/ambiguous SuperAdmin prevention, credential rotation requirement, idempotent restart, and refusal to promote an arbitrary pre-existing registrant. Existing bootstrap and user-admin service tests are the prior art.
- Appointment seam: system-admin handler tests cover appointing/revoking teachers, rejecting students/teachers, protecting the last SuperAdmin, auditing both success and denial, and ensuring the caller's platform role is the source of truth.
- Workspace seam: tenant handler/router tests cover unappointed users receiving 403 on create, appointed teachers and SuperAdmin creating only their own spaces, SuperAdmin retaining platform routes, teachers denied access to another teacher's workspace, and students denied workspace creation. Existing `tenant_self_service_policy_test.go`, RBAC middleware tests, and tenant route policy tests are the prior art.
- Student seam: authenticated tenant member and invitation HTTP tests cover invite-only registration, viewer-only links, email invitations and direct member-add, expired/revoked invitations, multi-workspace membership, and rejection of `owner`/`admin`/`contributor` through every member mutation API. Existing invite-only, register-by-invite, viewer-only invitation, tenant-member handler, and tenant route-policy tests are the prior art.
- Member-page seam: component tests render a workspace lead, a student, and an unexpected legacy membership. They assert the visible “空间负责人 / 学生” labels, absence of the role selector and generic role options, and a non-editable legacy warning. Tests assert rendered behavior and available actions rather than component internals.
- Migration seam: migration/service tests cover one-owner workspaces, idempotent downgrade of `admin`/`contributor` to `viewer`, audit records, and refusal to auto-resolve zero-owner or multi-owner workspaces. The migration result and persisted memberships are the contract, not SQL statement ordering.
- Model seam: model handler/service tests cover workspace isolation, teacher-only mutation, viewer read/use behavior, encrypted persistence, redacted API/audit/log output, and typed missing-configuration errors. Existing model handler, builtin model management, session model requirement, and tenant secret disclosure tests are the prior art.
- Regression matrix must include direct API calls and UI capability payloads for SuperAdmin, appointed Teacher, unappointed authenticated user, Student, unauthenticated visitor, and scoped API key principals.

## Out of Scope

- Implementing the backend, frontend, database migrations, or deployment changes in this specification task.
- A public teacher application/review workflow, organizational SSO, campus directory synchronization, or automatic identity verification.
- Student self-service password recovery through email/SMS; manual reset remains an operational fallback until separately specified.
- A platform-wide shared model pool, central API-key billing, automatic model fallback, or student-provided model keys.
- Fine-grained per-document ACLs beyond the existing workspace RBAC and resource ownership rules.
- Teacher or SuperAdmin daily access to another teacher's private conversations, model credentials, or workspace content outside a separately audited recovery action.
- Anonymous read access, public workspace discovery, or student-created personal workspaces.
- Defining visual styling beyond the required labels, visibility, warning, and removal of the role-promotion control.
- Introducing teaching assistants, co-teachers, delegated workspace administrators, or any replacement for legacy `admin`/`contributor`; these require a separate domain decision and specification.

## Further Notes

- Canonical domain terms are maintained in the root `CONTEXT.md`: SuperAdmin is the platform authority, Teacher is an appointed teaching identity, Student is a workspace consumer, and Workspace is the teacher-owned knowledge boundary.
- **运维默认（已落地）**：compose / `.env.example` 预设 `admin@admin.com` / `admin123`（空库自动创建唯一 SuperAdmin，首次强制改密）；小白上手见 [超级管理员上手手册.md](./超级管理员上手手册.md)。`auth.registration_mode` 默认 `invite_only`；`auth.default_tenant_mode` 默认 `tenantless`；`tenant.self_service_creation_enabled` 默认 `false`（仅拥有有效教师能力的身份可建空间，SuperAdmin 自动满足该条件）。
- 生产必须保持 `WEKNORA_TENANT_ENABLE_RBAC=true`；关闭时启动会打 ERROR 级告警。
- 邀请链路角色固定 `viewer`；模型凭据对 viewer 不可见；问答缺租户模型返回 typed `ErrModelSetupRequired`（2006），不回落平台 builtin。
- 用户身份标签（已落地）：后端在 `UserInfo` 上暴露统一平台身份分类 `platform_identity`（`superadmin`/`teacher`/`student`/`unset`，见 CONTEXT.md「用户身份标签 / 身份未设置 / 平台身份可见性」）。它对本人始终可见（`/auth/me`），超级管理员在教师管理范围内可见被管理账号的身份（教师任命/撤销/教师列表均返回 `UserInfo`）；工作空间成员名单（`TenantMemberResponse`）不携带该字段，只把内部 `owner` / `viewer` 展示为“空间负责人 / 学生”。
- 工作空间成员角色收敛为教育二态（#17 已落地）：前端取消角色下拉，展示「空间负责人 / 学生」；后端拒绝通过成员接口授予 `owner`/`admin`/`contributor` 或变更角色。历史 `admin` / `contributor` 迁移为 `viewer`（#18）与异常 Owner 显式恢复（#19）仍待实现；未迁移前成员页以不可编辑的历史角色警告展示。
- The existing `docs/教师学生超级管理员组织架构图.md` and rendered diagram visualize the intended hierarchy and teacher workspace isolation; this specification is the implementation contract.
