## Problem Statement

当前 WeKnora 把平台级 `is_system_admin`、空间内 `owner/admin/contributor/viewer` 和公开注册/自助建空间组合在一起，导致权限边界与教学场景不一致：普通注册用户可能创建个人工作空间并成为 Owner，系统管理员也可以有多个，且现有 bootstrap 只能提升已经注册的用户，不能建立部署时唯一的初始管理入口。教师之间还需要明确的空间隔离，学生不能获得开设空间或管理成员的能力。

教学部署需要一个可审计、默认拒绝的组织架构：部署时只有一个初始化超级管理员；超级管理员指定多个教师；教师分别创建和管理自己的工作空间；学生只能被教师邀请进入并使用被授权空间。模型服务由各教师按空间配置，超级管理员不承担统一模型供给和凭据托管。

## Solution

建立平台级唯一超级管理员（SuperAdmin）作为权限分发起点。其账号和初始密码在部署初始化阶段设定，并通过强制改密或一次性初始化流程完成首次登录。只有 SuperAdmin 可以任命或撤销教师身份；任何公开注册、学生操作或教师操作都不能把账号提升为教师或 SuperAdmin。

教师身份允许多个。教师可以创建多个属于自己的工作空间，并在这些空间内维护知识库、Agent、成员和模型配置；教师不能查看、修改或管理其他教师的工作空间。学生账号不具备创建工作空间能力，只能通过教师邀请进入一个或多个工作空间，默认以 `viewer` 身份使用知识资源。

公开的 Owner 自助注册和个人空间自动创建必须关闭。普通账号创建采用教师邀请流程（或由受授权的管理流程创建学生账号）；邀请只能授予学生使用权限，不能通过邀请生成教师、管理员或 Owner。所有平台级和空间级授权检查均默认拒绝，RBAC 强制模式必须开启。

模型配置按工作空间隔离。每名教师为自己的工作空间配置对话、向量化、重排、视觉/语音等需要的模型及凭据，承担对应的费用和配额。学生可以调用已配置模型，但不能读取、导出或修改凭据；SuperAdmin 只能审计配置状态，不能看到明文凭据。没有完成配置时，问答返回明确的配置缺失错误，不自动回落到平台模型。

## User Stories

1. As a deployment operator, I want to initialize exactly one SuperAdmin account with a predefined credential, so that there is a deterministic authority for the first login.
2. As a deployment operator, I want the initial credential to be changeable after first login, so that the bootstrap secret is not permanent.
3. As a SuperAdmin, I want to see all users, teachers, and workspaces at platform scope, so that I can audit the organization.
4. As a SuperAdmin, I want to appoint an existing account as a teacher, so that teacher identities come from an explicit approval action rather than self-registration.
5. As a SuperAdmin, I want to appoint multiple teachers, so that the platform supports multiple courses or teaching teams.
6. As a SuperAdmin, I want to revoke a teacher appointment, so that a departed teacher can no longer create or manage teaching workspaces.
7. As a SuperAdmin, I want teacher appointment and revocation actions to be audited, so that privilege changes are reviewable.
8. As a SuperAdmin, I want to remain the only platform authority, so that no teacher or student can appoint another SuperAdmin.
9. As a SuperAdmin, I want protection against removing the last SuperAdmin, so that the deployment cannot become ownerless.
10. As a SuperAdmin, I want to reset a teacher or student password without exposing the new password in logs, so that account recovery is operable and confidential.
11. As a teacher, I want to log in only after being appointed by the SuperAdmin, so that teacher access is centrally controlled.
12. As a teacher, I want to create a workspace after appointment, so that I can establish a course-specific knowledge area.
13. As a teacher, I want to create more than one workspace, so that I can separate courses, cohorts, or projects.
14. As a teacher, I want to become the owner of workspaces I create, so that I can maintain their content and members.
15. As a teacher, I want to invite students to my workspace, so that students can use the course knowledge area.
16. As a teacher, I want invitation links to grant only `viewer`, so that a forwarded student link cannot mint elevated workspace roles.
17. As a teacher, I want to add a trusted collaborator through a separate member-management flow, so that elevated workspace roles are not mixed with student invitations.
18. As a teacher, I want to remove or downgrade members in my own workspace, so that course access can be corrected.
19. As a teacher, I want to configure the models and provider credentials for my own workspace, so that I control quality, cost, and quota for that course.
20. As a teacher, I want model credentials encrypted at rest and redacted from responses, so that provider secrets remain private.
21. As a teacher, I want to see whether my workspace models are configured and healthy, so that I can fix setup before students ask questions.
22. As a teacher, I want a clear error when a required model is missing, so that failures are actionable instead of silently using an unexpected provider.
23. As a teacher, I want to manage my own workspace without seeing another teacher's workspace members, content, settings, or credentials, so that teaching spaces remain isolated.
24. As a teacher, I want to use more than one workspace I own, so that my account can support multiple teaching contexts.
25. As a student, I want to register only through a teacher invitation, so that arbitrary visitors cannot create teaching accounts or personal workspaces.
26. As a student, I want an accepted invitation to place me directly in the invited workspace, so that onboarding has no unrelated workspace-creation step.
27. As a student, I want to use documents, Agents, and configured models in an authorized workspace, so that I can complete course learning tasks.
28. As a student, I want my default role to be `viewer`, so that I cannot change course resources or member permissions.
29. As a student, I want to access multiple workspaces when multiple teachers invite me, so that one account can serve several courses.
30. As a student, I want to see only my own pending invitations and authorized workspaces, so that other students' identities and private spaces are not exposed.
31. As a student, I want model credentials hidden from the UI, API responses, logs, and exports, so that I cannot reuse a teacher's provider account.
32. As a student, I want a useful setup error when a teacher has not configured a required model, so that I know the issue is workspace setup rather than my account.
33. As an unauthenticated visitor, I want public registration and self-service workspace creation disabled, so that the deployment is not an open owner factory.
34. As any authenticated user, I want attempts to create a workspace without teacher authorization to return a clear 403, so that the permission boundary is consistent across UI and API.
35. As any authenticated user, I want attempts to appoint a teacher or SuperAdmin without platform authority to return a clear 403, so that privilege escalation cannot occur through direct API calls.
36. As a security auditor, I want cross-workspace access checks to enforce tenant isolation even when a user knows another workspace ID, so that identifiers cannot bypass authorization.
37. As a security auditor, I want denied role checks recorded with actor, workspace, action, and outcome, so that repeated probing is detectable.
38. As an operator, I want the system to fail closed if RBAC configuration is missing or disabled in production, so that a configuration mistake cannot turn every member into an effective Admin.
39. As an operator, I want migration behavior for existing Owners, Admins, and SystemAdmins documented, so that upgrading an existing deployment does not silently broaden access.
40. As a teacher, I want student conversations to remain private to the student unless a separately approved teaching feature says otherwise, so that workspace membership does not imply access to personal conversation content.

## Implementation Decisions

- Introduce explicit platform roles and invariants: exactly one active SuperAdmin at bootstrap, zero or more appointed Teachers, and Students as the default non-teaching identity. Preserve the distinction between platform authority and workspace membership roles.
- Replace the current multi-SystemAdmin interpretation with a single SuperAdmin authority for appointment operations. If backward compatibility requires retaining the existing flag, enforce a database/application invariant that only one active account can carry the highest platform role and provide an explicit migration for existing administrators.
- Bootstrap must create or atomically initialize the first SuperAdmin account and credential. It must not promote an arbitrary first registrant. The bootstrap credential is one-time/rotatable, and startup must refuse ambiguous initialization states rather than silently selecting a user.
- SuperAdmin-only endpoints manage teacher appointments, revocations, platform user status, and platform audit views. Teacher endpoints cannot mutate platform roles.
- Teacher appointment is a prerequisite for workspace creation. Workspace creation requests must evaluate the caller's current platform identity, not only a tenant role or client-controlled request field.
- A workspace has one or more teacher owners in the teaching domain, but a teacher can manage only workspaces where that teacher is an owner or explicitly authorized workspace administrator. No teacher receives an implicit cross-workspace bypass.
- Existing tenant RBAC remains the workspace-level enforcement mechanism, with `viewer < contributor < admin < owner`; production deployments must keep enforcement enabled. The fail-open observation mode is not an acceptable production default for this feature.
- Public self-service registration is disabled. The default provisioning mode for non-bootstrap users is tenantless until a valid teacher invitation is accepted; no registration path may create a personal workspace or Owner membership for an unappointed account.
- Student onboarding uses teacher invitations. Student invitation links are fixed to `viewer`; granting `contributor`, `admin`, or `owner` requires the authenticated teacher's member-management flow and is subject to workspace ownership checks.
- A student may belong to multiple teacher workspaces, with independent membership rows and no cross-workspace role inheritance.
- Teacher workspace model configuration is tenant-scoped and independent per workspace. Supported model categories follow the existing model service contracts; credentials are encrypted at rest, redacted from DTOs/logs/audit details, and never returned to viewers.
- Model invocation resolves the selected workspace configuration. Missing or invalid required configuration returns a typed, actionable setup error; there is no implicit SuperAdmin-provided fallback.
- SuperAdmin audit access exposes configuration status and security events without exposing plaintext provider credentials or student conversation bodies.
- All privileged mutations must be available through guarded backend routes first; frontend controls mirror the same capability checks and are not relied upon for security.
- Existing workspaces and memberships require an explicit migration policy: identify current SystemAdmins, map approved accounts to SuperAdmin/Teacher/Student, disable personal workspace creation, and review legacy Owner/Admin assignments before enabling enforcement.
- API keys and cross-tenant operator bypasses must not implicitly grant teacher appointment or SuperAdmin capabilities unless a separately declared platform capability is present.

## Testing Decisions

- Tests assert externally visible authorization behavior, response status/error shape, persisted role/membership effects, isolation, and secret redaction. They must not assert private helper structure or implementation-specific call ordering unless that ordering is the security contract.
- Highest seam: authenticated HTTP handler/router tests with controlled service doubles. This exercises route guards, identity extraction, request validation, and response behavior in one place while avoiding full deployment setup.
- Bootstrap seam: startup/bootstrap tests cover first initialization, duplicate/ambiguous SuperAdmin prevention, credential rotation requirement, idempotent restart, and refusal to promote an arbitrary pre-existing registrant. Existing bootstrap and user-admin service tests are the prior art.
- Appointment seam: system-admin handler tests cover appointing/revoking teachers, rejecting students/teachers, protecting the last SuperAdmin, auditing both success and denial, and ensuring the caller's platform role is the source of truth.
- Workspace seam: tenant handler/router tests cover unappointed users receiving 403 on create, appointed teachers creating only their own spaces, teachers denied access to another teacher's workspace, and students denied workspace creation. Existing `tenant_self_service_policy_test.go`, RBAC middleware tests, and tenant route policy tests are the prior art.
- Student seam: invitation registration and member-management handler tests cover invite-only registration, viewer-only links, expired/revoked invitations, multi-workspace membership, and denial of elevated roles through invitation APIs. Existing invite-only, register-by-invite, and viewer-only invitation tests are the prior art.
- Model seam: model handler/service tests cover workspace isolation, teacher-only mutation, viewer read/use behavior, encrypted persistence, redacted API/audit/log output, and typed missing-configuration errors. Existing model handler, builtin model management, session model requirement, and tenant secret disclosure tests are the prior art.
- Regression matrix must include direct API calls and UI capability payloads for SuperAdmin, appointed Teacher, unappointed authenticated user, Student, unauthenticated visitor, and scoped API key principals.

## Out of Scope

- Implementing the backend, frontend, database migrations, or deployment changes in this specification task.
- A public teacher application/review workflow, organizational SSO, campus directory synchronization, or automatic identity verification.
- Student self-service password recovery through email/SMS; manual reset remains an operational fallback until separately specified.
- A platform-wide shared model pool, central API-key billing, automatic model fallback, or student-provided model keys.
- Fine-grained per-document ACLs beyond the existing workspace RBAC and resource ownership rules.
- Teacher access to another teacher's private conversations, model credentials, or workspace content.
- Anonymous read access, public workspace discovery, or student-created personal workspaces.
- Defining the visual design of the administration console beyond the capability/visibility requirements.

## Further Notes

- Canonical domain terms are maintained in the root `CONTEXT.md`: SuperAdmin is the platform authority, Teacher is an appointed teaching identity, Student is a workspace consumer, and Workspace is the teacher-owned knowledge boundary.
- **运维默认（已落地）**：compose / `.env.example` 预设 `admin@admin.com` / `admin123`（空库自动创建唯一 SuperAdmin，首次强制改密）；小白上手见 [超级管理员上手手册.md](./超级管理员上手手册.md)。`auth.registration_mode` 默认 `invite_only`；`auth.default_tenant_mode` 默认 `tenantless`；`tenant.self_service_creation_enabled` 默认 `false`（仅 `is_teacher` 可建空间）。
- 生产必须保持 `WEKNORA_TENANT_ENABLE_RBAC=true`；关闭时启动会打 ERROR 级告警。
- 邀请链路角色固定 `viewer`；模型凭据对 viewer 不可见；问答缺租户模型返回 typed `ErrModelSetupRequired`（2006），不回落平台 builtin。
