## Problem Statement

当前教学部署的权限迁移存在四个相互关联的高风险缺口：

1. #17 之前创建的待处理邮件邀请或共享邀请链接仍可能保存 `admin` / `contributor` 角色。接受路径直接沿用邀请记录中的角色，因此历史邀请可以继续铸造超出教学二态模型的高权限成员。
2. 角色迁移被放在自动数据库迁移开关之内。采用外部 schema migration 并设置 `AUTO_MIGRATE=false` 的部署不会执行历史成员降权。
3. 成员降权成功后，审计写入失败会被吞掉。再次启动时该成员已经是 `viewer`，迁移不会重试，导致权限事实与审计事实永久不一致。
4. 异常 Owner 恢复在事务提交前通过事务外审计服务写入成功记录。如果后续事务回滚，系统会留下不存在的成功恢复审计。

这些问题会让学生获得管理能力、让升级行为依赖部署选项，并削弱安全审计对权限变更的可信度。

## Solution

将教学权限迁移、历史邀请归一化和异常 Owner 恢复纳入一个可重试、可验证的安全迁移流程：

- 所有邀请接受路径最终只创建 `viewer` 成员；历史仍处于 pending 的高权限邀请在升级时降为 `viewer`，并留下对应的迁移审计。已结束的邀请保留原始历史，不重新激活。
- 角色数据迁移作为 schema migration 完成后的独立启动步骤，无论 schema 是否由应用自动执行都必须运行。迁移未完成时，部署不得以“迁移成功”状态对外提供教学权限服务。
- 权限变更与成功审计在同一个数据库事务中提交；任一写入失败就回滚另一项，并让启动或恢复请求显式失败，以便重试。
- 异常 Owner 恢复的成员调整、异常记录关闭和恢复审计使用同一个事务边界，禁止在事务提交前调用事务外审计写入器。

## User Stories

1. As an operator upgrading an existing deployment, I want every pending invitation to grant at most `viewer`, so that an old invitation cannot bypass the teaching two-state model.
2. As an operator, I want pending email invitations with legacy elevated roles normalized to `viewer`, so that invitees can continue onboarding without inheriting obsolete management privileges.
3. As an operator, I want pending shared links with legacy elevated roles normalized to `viewer`, so that a bearer of an old link cannot gain management access.
4. As a student accepting any valid invitation, I want to become only a workspace student, so that invitation data cannot elevate my workspace permissions.
5. As a security auditor, I want each legacy invitation downgrade to record the old role, new role, workspace, invitation, actor, outcome, and reason, so that the upgrade is reconstructable.
6. As an operator using external database migrations, I want the teaching data migration to run even when `AUTO_MIGRATE=false`, so that security invariants do not depend on who applied the schema.
7. As an operator, I want startup to expose migration failure as an unhealthy or blocked state, so that the service cannot silently serve unresolved elevated memberships.
8. As a security auditor, I want a successful role downgrade to always have a durable success audit, so that the audit trail cannot under-report privilege changes.
9. As an operator, I want a failed audit write to roll back the corresponding role change, so that permissions and audit records remain consistent and a later retry is safe.
10. As a SuperAdmin resolving an ownership anomaly, I want member changes, anomaly resolution, and the success audit to commit atomically, so that the audit never claims a recovery that was rolled back.
11. As a SuperAdmin, I want a failed recovery to return an actionable error and leave the anomaly open, so that I can retry without guessing whether ownership changed.
12. As a security auditor, I want rerunning a successful migration to be idempotent, so that it does not create duplicate downgrade or recovery audit records.
13. As a workspace lead, I want newly created invitations and links to retain their existing viewer-only behavior, so that the historical-data fix does not reopen elevated role assignment.
14. As a deployment maintainer, I want the migration status and failure reason observable in logs and readiness checks without exposing invitation tokens or credentials, so that operations can diagnose the rollout safely.

## Implementation Decisions

- Treat `viewer` as the only role that invitation creation and invitation acceptance may materialize in a teaching deployment. The rule is enforced both at creation time and at the final membership-write boundary; persisted invitation role data is never trusted as an authority boundary.
- Add a versioned data migration for pending invitations whose role is `admin` or `contributor`. Convert those rows to `viewer`, including share-link rows, and emit one migration audit per changed invitation. Do not mutate accepted, declined, revoked, or expired invitation history; already-created memberships remain covered by the existing legacy-membership migration.
- Keep invitation acceptance idempotent and preserve the existing membership if the user is already a member, but never preserve an elevated role from an invitation during a new membership write.
- Run teaching data migrations in a post-schema startup phase that is independent of the `AUTO_MIGRATE` toggle. The phase must work after application migrations and after externally applied migrations, and must verify that required tables and indexes exist before declaring success.
- Make migration failure fail closed for the teaching service: startup/readiness must report failure and must not advertise the deployment as upgraded while legacy elevated access may remain. The failure must be retryable on the next startup.
- Introduce a transaction-aware audit writer or transaction-scoped audit repository. Membership/invitation updates and their success audit must use the same transaction and the same commit outcome. Audit errors are returned, not discarded.
- Execute ownership recovery, including demotion of other elevated memberships and closing the anomaly record, inside one transaction with its success audit. The audit actor is the authenticated SuperAdmin for an online recovery and a stable system actor for an automated migration.
- Preserve the existing domain glossary: the UI and external behavior use “空间负责人” and “学生”; `owner`, `admin`, `contributor`, and `viewer` remain internal enforcement values only.
- Preserve audit idempotency by emitting records only when a state transition actually changes data. A rerun after a committed transaction must report no new change and create no duplicate audit.
- Do not expose plaintext invitation tokens, provider credentials, or student conversation content in migration logs, readiness responses, or audit details.

## Testing Decisions

- Use the highest available authenticated HTTP seams for invitation acceptance and SuperAdmin recovery. Assert response status/error shape, persisted membership and invitation roles, anomaly status, and audit records; do not assert private helper structure or SQL statement order.
- Seed a pre-upgrade database with pending email and shared-link invitations carrying `admin` and `contributor`. Exercise every acceptance path and assert that the resulting membership is `viewer`; assert that terminal invitation history is unchanged.
- Run startup/bootstrap integration tests with both `AUTO_MIGRATE=true` and `AUTO_MIGRATE=false`, including a schema that was applied externally. Assert that legacy memberships and pending invitations are normalized in both modes.
- Inject an audit persistence failure during a downgrade. Assert that the role/invitation update rolls back, the migration reports failure, and a retry succeeds with exactly one audit record.
- Inject a failure after ownership membership updates but before anomaly resolution commits. Assert that all membership changes roll back, the anomaly remains open, and no success audit exists.
- Assert successful ownership recovery writes one atomic success audit containing actor, workspace, target, old role, new role, and outcome; rerunning it must not duplicate the record.
- Add readiness/startup tests for migration failure and retry, including missing required migration tables, without logging secrets.
- Reuse existing tenant invitation, tenant member, teaching-role migration, system recovery handler, and migration-schema test seams. Add only the minimum transaction-aware test double needed to force audit failures.

## Out of Scope

- Redesigning the broader RBAC model or introducing teaching assistants, co-teachers, delegated administrators, or new membership roles.
- Changing the invitation TTL, token entropy, link URL format, or registration UI beyond the viewer-only security guarantee.
- Rewriting historical terminal invitation rows or deleting audit history.
- Changing platform Teacher/SuperAdmin appointment policy, workspace isolation policy, model credential handling, or student conversation privacy.
- Replacing the existing audit taxonomy or building a new audit UI; this specification only requires durable, truthful records for the affected transitions.
- Fixing the separate P2 presentation issue where Owner counts are computed from a paginated member list.

## Further Notes

- This specification consolidates the P1 findings from the review of the five commits ending at `7ccffe1`.
- The source intent is the teaching permission architecture specification and `CONTEXT.md`, especially the requirements that teaching invitations are viewer-only, legacy elevated memberships are downgraded with an audit record, and ownership recovery is explicit and auditable.
- The implementation should be released as a backwards-compatible security/data migration. Operators must be told that pending legacy invitations will lose elevated role semantics and that a failed migration requires remediation before readiness.
