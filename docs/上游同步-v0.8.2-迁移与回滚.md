# 上游同步 v0.8.2 · 迁移与回滚剧本

> 分支：`sync/upstream-v0.8.2`（基座 `v0.8.2`）  
> 日期：2026-10-01  
> 状态：Ticket 0 迁移落地中；**禁止对源卷 `down -v`**

---

## 1. 问题

川农在 `v0.8.0` 之上占用了 `000091`–`000098`；上游 `v0.8.2` 用同一组号做了 MCP / browser / memory / fork 等。两边 SQL 语义不同，不能直接 `migrate up`。

## 2. 代码侧方案（已落地）

| 路径 | 内容 |
| --- | --- |
| 上游 `091`–`110` | 保留 `v0.8.2` 原件 |
| 川农教学 | 顺延为 **`000111`–`000116`**（Postgres） |
| SQLite 教学 | 顺延为 **`000031`–`000036`**（上游 sqlite 止于 `030`） |

编号映射：

| 新号 | 原川农号 | 主题 |
| --- | --- | --- |
| 111 / sqlite 031 | 091 / 016 | `default_agent_id` |
| 112 / 032 | 097（终态 notes） | `tenant_notes` |
| 113 / 033 | 098（终态 announcements） | announcements |
| 114 / 034 | 094 / 013 | platform identity |
| 115 / 035 | 095 / 014 | ownership anomalies |
| 116 / 036 | 096 / 015 | single active share link |

原 `092`/`093` 与 `097`/`098` 内容等价（`IF NOT EXISTS`），换基后只保留终态一份。

教学迁移普遍使用 `IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`，因此 **Route 2 在已有川农 schema 上再跑 `111`–`116` 应为幂等空操作**。

## 3. Route 1：空库

1. 新 `COMPOSE_PROJECT_NAME` + **新 volume**（勿挂旧卷）。  
2. 启动 app / `scripts/migrate.sh up`。  
3. 期望：`schema_migrations.version = 116`，`dirty=false`。  
4. 失败回滚：`docker compose down -v` **仅对该 QA project**（新卷可删）。

不需要桥接脚本。

## 4. Route 2：克隆升级（现网/开发库语义）

前置：源卷只读克隆（见 `scripts/sync-v082/clone-postgres-volume.sh`）。

假设克隆库当前：`version=98`，且 `091`–`098` 行对应的是**川农** SQL（不是上游）。

### 4.1 正向步骤

```text
1. CONFIRM=YES bash scripts/sync-v082/clone-postgres-volume.sh
2. 用克隆卷起独立 compose（例：weknora-sync-v082-upgrade）
3. CONFIRM=YES PSQL_CMD='docker exec -i <pg> psql -U postgres -d WeKnora' \
     bash scripts/sync-v082/bridge-apply-upstream-091-098.sh
   → 手工执行上游 091–098 SQL；schema_migrations 仍为 98
   → ledger：sicau_v082_bridge_ledger
4. 启动 sync 镜像，AUTO_MIGRATE=true
   → 自动跑 099–110，再跑 111–116（幂等）
5. 确认 version=116、dirty=false，再跑教学冒烟
```

### 4.2 失败回滚（默认策略）

| 失败点 | 做法 |
| --- | --- |
| 克隆未完成 | 删未完成的 dest volume；源卷不动 |
| 桥接中途失败 | **丢弃克隆卷**；查 `sicau_v082_bridge_ledger` 仅作诊断；**不要**在源卷 `force` |
| `migrate up` 中途 dirty | 克隆上可按官网 `AUTO_RECOVER_DIRTY` / `migrate force` 抢救；抢救失败仍 **丢弃克隆** 重来 |
| 冒烟失败但库已到 116 | 业务回滚 = 丢弃克隆，继续用源卷上的旧栈；代码仍在 sync 分支 |

**唯一推荐的硬回滚：删除克隆 volume。** 不在源卷做 `migrate down`，不对源卷 `down -v`。

### 4.3 禁止

- 对 `weknora_postgres-data`（或生产卷）跑桥接 / `force` / `down -v`  
- 在 `version≠98` 的库上盲跑桥接  
- 桥接失败后改源库 `schema_migrations` 假装成功  

### 4.4 SQLite 旧教学库升级

旧教学 SQLite 的 `013`–`018` 与上游同号但语义不同。应用迁移器识别旧教学
身份字段和缺失的 MCP `enabled` 字段，在同一个事务内补跑被遮住的上游
`013`–`018`，不重写迁移版本账本。随后正常推进至 `036`；重编号后的
`031` / `034` 仅补缺失字段，不覆盖已有默认 Agent、教师标志、笔记或公告。

- 先备份并在副本上启动新版本，保持 `AUTO_MIGRATE=true`。
- 预期：`version=36`、`dirty=false`，MCP enabled / browser / session fork 结构齐全。
- 桥接失败整笔回滚，版本保持原值，启动报告失败；修复原因后可重试。
- 该桥接由应用执行，不能只对旧教学库直接按新编号运行 SQL 文件。
- 验证覆盖旧版本 `13`–`18`、数据保留、重复启动，以及中断桥接后的回滚/重试。
